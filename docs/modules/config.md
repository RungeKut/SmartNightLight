# ConfigStore.h — настройки в EEPROM

Все настройки лежат одной структурой `ConfigData` по смещению 0, с магическим
числом в первом поле.

```cpp
#define EEPROM_MAGIC 0x4E4C   // 'NL'
```

## Что внутри

| Поле | Тип | Назначение |
|------|-----|-----------|
| `magic` | `uint16_t` | признак инициализации |
| `wifiSSID` | `char[32]` | пустой = поднять точку доступа |
| `wifiPass` | `char[64]` | клиенту никогда не отдаётся |
| `deviceName` | `char[32]` | пустое = имя по MAC |
| `flags` | `uint8_t` | маска включённых режимов, `nl::FLAG_*` |
| `manualBrightness` | `uint8_t` | яркость ручного включения |
| `sleepTime` | `uint16_t` | hhmm |
| `sleepLength` | `uint8_t` | минут |
| `signalBrightness` | `uint8_t` | вспышки и старт затухания |
| `sunriseTime` | `uint16_t` | hhmm |
| `sunriseLength` | `uint8_t` | минут |
| `sunLength` | `uint8_t` | минут |
| `sunriseBrightness` | `uint8_t` | максимум рассвета |
| `tzOffsetMinutes` | `int16_t` | смещение от UTC, по умолчанию 180 |
| `_reserved` | `uint8_t[16]` | место под новые поля |

Ручное включение (`manualOn`) в EEPROM **не сохраняется**: после перезагрузки
светильник должен вернуться к расписанию, а не остаться включённым.

## Зачем магическое число

Первая версия прошивки писала поля по фиксированным адресам:

```cpp
EEPROM.get(2, sleepTime);
EEPROM.get(4, lengthSleepTime);
```

Признака того, что память вообще инициализирована, не было. На чистой плате
оттуда читались байты `0xFF`, и `sleepTime` становился 65535 — дефолты из
кода затирались мусором ещё до первого запуска.

Сейчас не совпал `magic` — берутся значения по умолчанию. На тестовой плате
это видно в логе при первой прошивке поверх старой версии:

```
[Config] EEPROM пуста или чужая (magic=0x6432), беру умолчания
```

## Расширение структуры

**Новые поля добавлять только в конец.** Тогда смещения прежних полей не
меняются, `magic` остаётся валидным, и настройки переживают обновление
прошивки.

В байтах за прежним размером структуры лежит `0xFF` из стёртой flash, поэтому
каждое новое поле должно уметь распознать это значение как «не задано».
Пример — `tzOffsetMinutes`: `0xFFFF` как `int16_t` даёт −1, и санитайзер
возвращает значение по умолчанию.

Если порядок или размер существующих полей всё же меняется — **обязательно
меняйте `EEPROM_MAGIC`**, иначе старые данные прочитаются как новая структура
и разъедутся по полям.

## Санитайзер

Магическое число подтверждает, что память инициализирована, но не то, что
значения осмысленны: обрыв питания посреди записи или новое поле в хвосте
дают мусор с валидным `magic`. Поэтому `sanitize()` при загрузке:

- завершает строки нулём;
- проверяет `hhmm` на осмысленность (часы ≤ 23, минуты ≤ 59);
- загоняет часовой пояс в диапазон −720..840.

Строка из EEPROM может не содержать нуля вовсе. Если все 32 байта равны
`0xFF`, цикл вида `for (i = 0; s[i]; i++)` уйдёт читать соседнюю память —
поэтому `terminate()` всегда получает размер буфера, а не только указатель.
То же правило действует для `sanitizeDeviceName()` в `.ino`.

## Износ flash

Ресурс EEPROM у ESP8266 — около 100 000 циклов записи.

Дополнительной защиты не требуется: `EEPROM.put()` в ядре сравнивает буфер с
текущим содержимым и выставляет `_dirty` только при реальном отличии, а
`commit()` при `!_dirty` выходит сразу. Сохранение без изменений физически
ничего не пишет.

Но ползунок яркости шлёт значение на каждое движение, и каждое из них
отличается от предыдущего. Поэтому в `.ino` есть отложенная запись:

```cpp
markConfigDirty();   // запомнили момент
// flushConfig() запишет через SAVE_DEFER_MS = 30 секунд после последнего движения
```

Отложенная запись сбрасывается принудительно перед плановой перезагрузкой,
чтобы не потерять последнее значение.

> В первой версии эта же задача решалась экзотичнее: момент записи
> откладывался на 6 часов и хранился в виде интервала, а `checkTimespan()`
> проверяла, не пора ли. Побочный эффект — при перезагрузке раньше срока
> настройки терялись.
